01 · Definizione

Cos'è MORPHEUS•JLX™

MORPHEUS•JLX™ è il motore di sanificazione, deduplicazione e normalizzazione del KREATIO UNIVERSAL SYSTEM™. Il suo nome richiama la sua capacità di "vegliare" sul flusso informativo, garantendo che ogni record che entra nel database sia puro, univoco e conforme alle stringenti regole di ATLAS•EVENTA™. Agisce come filtro pass-or-fail: o il dato supera il controllo, o non entra nel database.

T.C.F.™ — La Mente
Normativa
Definisce le regole di coerenza. Stabilisce cosa è giusto: criteri culturali, territoriali, ontologici. È il guardiano concettuale del sistema.
MORPHEUS•JLX™ — La Mano
Operativa
Implementa la logica sul flusso di dati. Esegue come viene pulito e integrato: deduplicazione, normalizzazione, versioning. È l'esecutore operativo del sistema.
02 · Funzioni Core

I Quattro Motori Operativi

FUNC · 01
Deduplicazione Intelligente
Parent–Child
Analizza in tempo reale ogni nuova immissione per verificare se l'entità esiste già. Se il record è già presente, impedisce la creazione di un duplicato e forza il sistema a generare esclusivamente una nuova Istanza Temporale collegata al PARENT_ID esistente.
PARENT_ID · INSTANCE LINK
FUNC · 02
Anti-Rumore
Applica filtri algoritmici per eliminare elementi di disturbo: articoli inutili, caratteri speciali, formattazioni errate, testo non normalizzato. È il responsabile della pulizia che rende il database "Clean" e leggibile da qualsiasi sistema downstream.
NOISE FILTER · CLEAN OUTPUT
FUNC · 03
Normalizzazione Rigorosa
Forza ogni dato a rispettare il set chiuso di campi definiti. Se un dato non può essere ricondotto alla struttura canonica, viene scartato o parcheggiato per revisione, ma mai inserito in forma corrotta. Un evento deve avere lo stesso Nome Normalizzato indipendentemente dalla fonte.
CLOSED FIELD SET · STRICT SCHEMA
FUNC · 04
Gestione del Versioning
Poiché non è consentito sovrascrivere i dati (per mantenere la tracciabilità storica), gestisce il versioning di ogni modifica. Ogni aggiornamento è registrato con timestamp e fonte, creando una catena di custodia del dato che garantisce l'auditabilità totale.
IMMUTABLE · CHAIN OF CUSTODY
03 · Schema

Set Chiuso di Campi Normalizzati

Struttura Canonica · MORPHEUS•JLX™ Output Schema
EVENT_ID STRING Identificativo univoco progressivo dell'entità logica. Non riassegnabile. Non sovrascrivibile. REQUIRED
INSTANCE_ID STRING Identificativo dell'occorrenza temporale. Collegato al PARENT_ID (EVENT_ID) dell'entità madre. REQUIRED
PLACE_ID STRING Riferimento al luogo certificato. Deve corrispondere a un codice ISTAT verificato nel database territoriale. REQUIRED
EVENT_NAME_NORMALIZED STRING Nome dell'evento dopo normalizzazione: rimozione articoli, capitalizzazione standard, eliminazione caratteri speciali non ammessi. REQUIRED
CATEGORY ENUM Categoria tassonomica chiusa: FESTA_RELIGIOSA | SAGRA | PALIO | RITO_AGRARIO | MERCATO. REQUIRED
DATE_START ISO 8601 Data di inizio dell'istanza temporale. Formato obbligatorio: YYYY-MM-DD. REQUIRED
DATE_END ISO 8601 Data di fine dell'istanza temporale. Può coincidere con DATE_START per eventi di un giorno. REQUIRED
MORPHEUS_VERSION STRING Versione del motore che ha processato il record. Per audit trail. REQUIRED

04 · Garanzie

Le Tre Garanzie Inviolabili

1
ID Non Consumato Inutilmente
Se un record è uno scarto, l'ID non avanza. La VINCOLO DI NUMERAZIONE ID è rispettata in modo assoluto: ogni ID progressivo corrisponde a un'entità certificata e di valore, mai a un duplicato o a un dato corrotto.
2
Coerenza del Nome Normalizzato
Un evento deve avere lo stesso EVENT_NAME_NORMALIZED indipendentemente dalla fonte che lo riporta. MORPHEUS•JLX™ garantisce che "Festa del SS. Crocifisso" e "Fest. del Santissimo Crocifisso" vengano ricondotti alla stessa entità canonica.
3
Integrità del Sistema Inviolabile
Filtro pass-or-fail assoluto: o il dato supera il controllo di pulizia e deduplicazione, o non entra nel database. Non esiste una via di mezzo. I record parcheggiati per revisione umana sono tracciati con status FLAGGED, mai inseriti come VALIDATED.
05 · Logica Operativa

Pass-or-Fail · Casistiche

✓ PASS → STATUS: CLEAN
Record con tutti i campi obbligatori compilati correttamente
Nome normalizzabile secondo le regole del motore
Coordinate e ISTAT verificati nel database territoriale
Entità non presente come duplicato nel database
Categoria appartenente al set chiuso ammesso
Date in formato ISO 8601 valido
✗ FAIL → STATUS: REJECTED / FLAGGED
Campo obbligatorio assente o nullo → REJECTED
Duplicato esatto rilevato → REJECTED (istanza collegata a PARENT)
Duplicato sospetto (similarity > 85%) → FLAGGED per revisione
Categoria non appartenente al set chiuso → REJECTED
Coordinate non verificabili con ISTAT → FLAGGED
Testo non normalizzabile automaticamente → FLAGGED
