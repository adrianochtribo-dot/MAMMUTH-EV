01 — Cos'è

Definizione

ATLAS•EVENTA™ non è un calendario. È il core informativo e il motore operativo del sistema.

Mappa l'identità culturale delle comunità attraverso i loro eventi, con un principio architetturale preciso: separare l'entità dell'evento (cosa è) dal suo dato temporale e geografico (quando e dove accade). Questa separazione è ciò che impedisce i duplicati e permette una memoria storica precisa.

02 — Fondamenti

Architettura del sistema

Entity / Instance Split
⊗ Entità vs Istanza

L'evento (cosa è) è distinto dalle sue occorrenze nel tempo (quando accade). Niente duplicati, storico preciso.

Geo · ISTAT · Coords
◎ Ancoraggio territoriale

Ogni luogo geolocalizzato con coordinate e codice ISTAT. Senza riferimento geografico univoco, l'evento non entra.

MORPHEUS·JLX™ + T.C.F.™
⊕ Pipeline di validazione integrata

MORPHEUS·JLX™ pulisce e deduplica; T.C.F.™ verifica coerenza culturale e priorità territoriale. Sono i guardiani del dato.

Lo schema separa entità e istanza così:

{
  "entity": {              // immutabile
    "id": "ev-laz-0042",
    "nome": "Infiorata di Genzano",
    "tipo": "FESTA_RELIGIOSA",
    "istat_comune": 058041,
    "coordinate": { lat: 41.7001, lng: 12.6876 }
  },
  "instance": {            // ricorrente
    "entity_ref": "ev-laz-0042",
    "data_inizio": "2026-06-14",
    "edizione": 97,
    "tcf_status": VALIDATED
  }
}
03 — Gerarchia

Priorità di saturazione

Il database si riempie per priorità, non a caso. Prima il DNA culturale più profondo.

  • I
    Riti religiosi / feste patronaliPriorità assoluta. Continuità storica plurisecolare, fonte documentale verificabile.
  • II
    Sagre territoriali canonicheAlta priorità. Identità agroalimentare, preferibilmente IGP/DOP/DOC o tradizioni stagionali.
  • III
    Palii / giostre / rievocazioniPriorità standard. Data storica d'origine obbligatoria. Solo dopo la saturazione di I e II.

Solo dopo aver saturato le priorità si integrano altre tipologie (cultura, sport, svago). Sempre privilegiando l'accuratezza sulla quantità.

04 — Regole immutabili

Caratteristiche non negoziabili

RULE · 01
ID sequenziale

Identificativo progressivo obbligatorio. Mai riassegnabile. Niente duplicati né buchi logici.

RULE · 02
Versioning obbligatorio

Vietato sovrascrivere. Storico completo per ogni record, auditabilità totale.

RULE · 03
Family-Centric

Pensato per famiglie e comunità. Accesso chiaro, immediato, senza logiche commerciali.

RULE · 04
Anti-Ranking

Nessuna classifica o promozione. Solo fedeltà storica e sociale dell'evento al territorio.

06 — Da fare

Lavoro aperto

Tracciato. Lo stato va confermato sul database reale, non assunto.

  1. Verificare la separazione Entity / Instance nello schema reale.

    Il documento la prevede; controllare se la tabella su Supabase la implementa o se entità e istanza sono fuse. Se fuse → da risolvere.

  2. Costruire il bulk ingest idempotente.

    Caricare centinaia di eventi senza duplicati. Serve una chiave d'identità deterministica + UPSERT, coerente con la RULE 01 (ID sequenziale) ma adatta al carico automatico.

  3. Conteggio reale e distribuzione per comune.

    Chiudere il disallineamento sui numeri con select count(*) e group by istat_comune. Verificare che ogni evento porti il codice del comune giusto.

  4. Geocoordinate mancanti.

    Eventi senza lat/lng non compaiono in mappa. Censire quanti restano e completarli.

Quando un caposaldo si chiude, si aggiorna il Build Status in cima — e solo dopo verifica dal vivo, mai per dichiarazione.
